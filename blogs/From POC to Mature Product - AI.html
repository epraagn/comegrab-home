From a 50-line script to a real AI product: add tools only when pain appears

A six-month story of how an AI product grows from a 50-line script to a real system, and the tool a team picks up each time a specific pain appears.

Most AI products do not start as a big framework. They start as a short script that works, and grow one problem at a time. Here is the story of one such product over six months, and the tool the team picked up each time a real pain appeared.

Chapter 1 · Day 1: It works

You write a simple bot: PDFs, chunks, a vector database and one model call. You call the model through the Anthropic SDK directly.

  • Cost per answer: about $0.0035.
  • Everything is visible and simple.

Tool they reach for: the Anthropic SDK. Nothing more is needed yet.

Chapter 2 · Week 2: The glue code piles up

Users want Word files, web pages and a database as sources. Someone asks, “Can we try a different vector database or model?” Every swap means rewriting code.

The team reaches for LangChain: ready-made loaders, retrievers and prompt templates, chained in a line.

Chapter 3 · Month 1: The first wrong answer

A user complains. You open the logs and see only the final answer. Was retrieval wrong? Was the prompt wrong? Which step took 8 seconds? No idea.

The team adds tracing with Langfuse or LangSmith. Now every request shows each step, the tokens, the cost and the chunks retrieved. The failed case is saved as a test.

Chapter 4 · Month 2: The flow gets complicated

New rules arrive: classify the question, retrieve, draft, have a human approve risky answers, and retry on failure. A server restart loses half-finished requests. A straight chain cannot loop or wait.

The team moves to LangGraph: a graph with branches and loops, and saved state so a run resumes after a crash or waits days for approval.

Chapter 5 · Month 3: Prompt whack-a-mole

Every hand-edited prompt fixes one question and breaks another. A model upgrade breaks several.

The team builds an eval set (questions with correct answers) and a score. Then DSPy tunes the prompt against that score instead of by guesswork.

Chapter 6 · Month 4: “Can it do the research itself?”

The product now needs to read 20 documents, compare them, write a report and save it. That is an agent loop: think, use a tool, read the result, repeat. Writing it safely by hand is slow.

The team uses the Claude Agent SDK: the loop, file and search tools, permissions and hooks come built in. Safety rules go in as permissions, spend limits and hooks that block bad actions.

Chapter 7 · Month 5: The multi-agent temptation

Someone proposes a researcher, a writer and a reviewer, each its own agent. CrewAI makes that easy. It works, but LLM calls triple, and so do cost and latency.

The tracing from Chapter 3 shows the reviewer agent adds little. The team keeps two agents.

Chapter 8 · Month 6: The cost audit

Finance asks why the bill grew 8x. The trace and cost data point to long prompts, an agent loop that repeats tool calls, and thinking tokens.

The team trims context, caches repeated questions and sets per-user budgets. These are the basic guardrails from day one, grown up.

The lessons to remember

RuleMeaning
A tool earns its place only when a specific pain appears.Do not start with a framework. Start with the SDK and add tools as problems show up.
Tracing comes early.You cannot fix or price what you cannot see.
More agents means more cost.Add them only when the data says so.
