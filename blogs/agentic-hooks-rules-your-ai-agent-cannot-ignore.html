Agentic hooks: rules your AI agent cannot talk its way around

A plain-language guide to hooks, the fixed checkpoints that let a business control what an AI agent may do, instead of just asking it nicely in a prompt.

Give an AI agent access to your files, your email or your customer records, and one question matters more than any other: what stops it from doing the wrong thing? Most teams answer with a sentence in the prompt, such as “never delete customer data.” That sentence is a request, not a rule. A hook turns it into a rule.

What a hook is

A hook is a small piece of ordinary code that the system runs at a fixed moment in the agent’s work, every single time. For example, just before the agent uses a tool, or just after it edits a file. The hook looks at what is about to happen (or what just happened) and makes a decision. The AI model does not get a vote on whether the hook runs.

The key word is fixed. A prompt depends on the model reading, remembering and choosing to follow it. A hook depends on nothing but the code. It behaves the same on a calm Monday and in the middle of a confusing, multi-step task.

Prompts ask, hooks enforce

Instruction in a promptHook
Who decidesThe modelYour code
Can it be skippedYes, if the model forgets or is misledNo, it runs at that step every time
Best forStyle, tone, preferencesLimits, approvals, safety, records
Can you prove it ranHard to sayYes, it can write a log entry

Where hooks sit

  • Before an action. Check a request to use a tool, send a message or call a system, then let it through or stop it.
  • After an action. Check what a tool returned, or what a file edit changed, before the agent moves on.
  • When information is fetched. Strip out documents or fields the agent should never see.
  • At approval points. Pause a risky step until a person says yes.
  • At the end. Confirm the work meets your checklist before it counts as done.

What a hook can decide

A hook is not just a stop sign. It can allow the step, block it with a reason the agent can read, change it (for example, mask a phone number), add useful context, or send it to a person for approval. In every case it can leave a record of what it saw and what it chose.

Everyday examples

  • A coding assistant edits a file. A hook runs the tests and the security scan straight away, and rejects the change if either fails.
  • A support agent drafts an email. A hook blocks it if the address is outside your approved domains.
  • A finance assistant wants to approve a payment. A hook sends anything above a set amount to a manager first.
  • A research agent pulls documents. A hook removes personal data and confidential files before the model reads them.
  • Any agent using a production system. A hook refuses delete and overwrite commands and logs the attempt.

What can go wrong

  • Friction. Every check adds a little time, and every approval needs a person. Put hooks where the risk is real, not on every step.
  • A weak hook is a false comfort. If the check can be sidestepped, people will believe the agent is controlled when it is not.
  • A missing hook means no control. An agent with no checkpoint on a risky action simply has the permission it was given.
  • Problems show up late. A flawed hook is often found only after the agent has done something it should not have.

How to get started

  1. List what your agent can touch: files, systems, money, messages, customer data.
  2. Mark the actions that would hurt most if they went wrong or could not be undone.
  3. Put a hook on each of those, starting with “block,” “ask a person” and “log.”
  4. Tie each decision to who the agent is acting for and why, not just to the fact that it is logged in.
  5. Treat hook code like any other critical code: review it, test it, version it, and re-check it whenever the agent gains a new ability.

The point

The more freedom an agent has, the less you can rely on good intentions written in a prompt. Use prompts to guide the agent’s work and hooks to guard the edges. If the answer to “what stops it?” is a line of code that always runs, you have a control. If the answer is “we asked it not to,” you have a hope.
