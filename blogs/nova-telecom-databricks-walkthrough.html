The story and the six planted events

The architecture

Source files (PM, FM, syslog, inventory, tickets, CRM, OMS, CDR, billing) land in one volume. They are loaded into bronze (raw, with audit columns), cleaned in silver (typed, deduplicated, harmonized, with history), and turned into gold (health, SLA, root cause, churn risk, capacity plan). Dashboards read gold.

OSS is network-facing: inventory, PM, FM, syslog, tickets, provisioning. BSS is customer and revenue-facing: CRM, orders, billing, complaints. The CDR is the bridge, because it carries both a customer (IMSI) and a cell. Joins use cell_id, site_id, imsi and customer_id.

Suggested 15-minute demo flow

  1. Executive Summary: state the six findings first.
  2. NOC: the 20 Sep fiber cut, from availability to alarms to SLA breaches.
  3. Optimization and Root Cause: Nokia R22.3, then the tilt change, congestion and the capacity plan.
  4. Customer and Provisioning: the day-3 bug, then churn risk bands and the cell-quality link.
  5. Behind the scenes: the pipeline graph with its quality rules, the job run, and the table lineage in Catalog.

Be honest about these limits

  • The data is synthetic, and the dashboard titles say so.
  • The Executive findings table is typed by hand from our outputs. Step 34 verifies each line against its source table.
  • The churn score is rule-based and was tested on the data it was designed around. Step 32 adds a trained model with a train/test split.
  • Only the PM chain runs as a declarative pipeline. The rest ran as scripts, and the pipeline is the pattern to extend.
  • I have only seen a screenshot of Dashboard 1 (NOC). The values for Dashboards 2, 3 and 4 are the ones our tables should produce, so check them on screen before presenting.
  • Free Edition limits apply. A job schedule was not confirmed.
  • Some early estimates were corrected by real outputs (1,781 tickets, not about 2,900; Nokia R22.3 alarms up about 9x, not 7x). This page uses the real numbers.

Design: lifecycle, OSS and BSS split, 28 tables, the story

Phases 1 to 4. No code.

Context. Before touching any tool, we needed to know what a telco data platform has to hold. We used the four-phase lifecycle: Network Planning, Deployment and Configuration, Services Fulfillment and Activation, and Operations (assurance, optimization, healing).

What we did.

  • Split each phase into OSS and BSS activities.
  • Designed about 28 tables with keys and grain (for example, one row per cell per 15 minutes for PM).
  • Wrote the story and chose six events to plant, each with an answer table.

Why. The data generator needs columns, keys and relationships. A wrong join key found on paper costs a minute; found after millions of rows it costs hours. The story gives every table a purpose.

How. Paper design: table list tagged OSS/BSS, joins on site_id, cell_id, imsi, customer_id, medallion mapping.

What it produced. 28 tables across 4 phases. Phase 3 is mixed (BSS captures the order, OSS provisions it). Phase 4 is the richest.

What to tell the client. A telco's data comes from two worlds: the network (OSS) and the customer and revenue systems (BSS). The value is in joining them, for example linking a complaint to the quality of the cell the customer uses. We designed that join before writing any code.

Steps 1-8: Environment (Databricks Free Edition and VS Code)

Platform setup.

Context. Databricks is a cloud platform, so nothing is installed. You sign up for a workspace and connect your editor to it.

What we did.

  • Signed up for Databricks Free Edition (no credit card).
  • Installed the Databricks CLI, created a Python 3.12 virtual environment, and installed databricks-connect, pandas, faker, numpy.
  • Logged in with the CLI (profile DEFAULT) and ran a test that printed "Nova Telecom is live".

Why. Databricks Connect lets code written in VS Code run on Databricks serverless compute. Python 3.15 was too new for it, so we used 3.12. A virtual environment keeps the project reproducible.

How.

  • winget install Databricks.DatabricksCLI
  • py -3.12 -m venv .venv and Set-ExecutionPolicy RemoteSigned for the PowerShell script policy
  • pip install databricks-connect pandas faker numpy, with requirements.txt
  • databricks auth login, then DatabricksSession.builder.serverless(True).getOrCreate()

What it produced. A live workspace, CLI v1.22.1, Python 3.12.10 in the venv, and a test query that ran on serverless compute.

What to tell the client. Nothing to install on their side. The platform is cloud-based, compute is serverless, and the team keeps using the tools it already has.

Watch out. Always activate the venv (.venv\Scripts\activate) before running scripts. One run failed with "No module named databricks" because it was not active.

Step 9: Data platform structure (Unity Catalog)

Platform setup.

Context. Unity Catalog is Databricks' governance layer. Data is organized as catalog, then schema, then table or volume.

What we did. Created catalog nova_telecom, schemas bronze, silver and gold, and volume bronze.raw as the landing zone for files.

Why. Each layer has one job. Bronze keeps data exactly as the source sent it, silver is cleaned and trusted, gold is the business view. A volume holds raw files before they become tables.

How. setup.py with CREATE CATALOG, CREATE SCHEMA three times, and CREATE VOLUME nova_telecom.bronze.raw.

What it produced. An empty structure ready for data.

What to tell the client. Every source system drops its files in one landing zone. Bronze is the untouched copy, silver is trusted data, gold is what business users read. If a number looks wrong, we can trace it back to the exact source file.

Step 10: Network inventory exports (site, cell, equipment)

Phase 2, Deployment. OSS.

Context. After sites are built, the OSS inventory holds what exists: sites, cells, and the radio equipment on them.

What we did.

  • Generated 200 sites (4 regions, Ericsson and Nokia, 20 new Pune sites), 604 cells (4G/5G, band, azimuth, tilt) and 604 equipment records with software version, and wrote them as CSV into the landing zone.
  • Planted event 2: about half of the Nokia cells run software R22.3. Ericsson never does.

Why. This is the master data every later table joins to. The software version is what lets us later prove that one vendor's upgrade causes trouble.

How. gen_master.py: pandas and numpy with a seeded generator, then WorkspaceClient().files.upload() to /Volumes/nova_telecom/bronze/raw/.

What it produced. site 200 rows, cell 604, equipment 604. Nokia: R21.1 on 133 cells, R22.3 on 107. Ericsson: R21.1 on 244, R21.2 on 120.

What to tell the client. This is the same kind of file an inventory system exports after rollout: where each site is, what antennas it has, and what software the radios run. Software version is the key to one of our findings.

Watch out. The files live in the Databricks volume, not on your laptop. Browse them under Catalog, nova_telecom, bronze, raw.

Step 11: Bronze load of inventory (batch ingest)

Phase 2, Deployment. OSS.

Context. Files are not practical to query at scale. Ingest means copying raw data from files into a table, unchanged, and stamping each row with where it came from.

What we did. Read the three CSVs into Delta tables bronze.site, bronze.cell, bronze.equipment and added audit columns _ingest_ts and _source_file.

Why. A batch read is enough for small one-time files. Bronze keeps a permanent, traceable copy of what the source sent. No cleaning happens here.

How. ingest_master.py with spark.read, inferSchema, saveAsTable and mode("overwrite"). This script has no memory of what it loaded, so every run overwrites the table.

What it produced. 200, 604 and 604 rows. Timestamps are stored in UTC (IST minus 5:30).

What to tell the client. Every row carries its source file and load time, so any number can be traced back to the file that delivered it. That is the basis for auditability.

Step 12: Validation and a first look at Delta

Phase 2, Deployment. OSS.

Context. Before building on a table, check it behaves. Delta Lake is the table format underneath: files plus a transaction log.

What we did. Ran inventory-style queries (sites per region and vendor, software by vendor) and looked at DESCRIBE HISTORY and DESCRIBE DETAIL.

Why. It confirmed the Nokia R22.3 plant was in the data, and showed that every write is a numbered version, which later powers time travel.

How. explore_delta.py with GROUP BY and JOIN queries.

What it produced. Pune has 60 sites (39 Ericsson, 21 Nokia). Delta history showed version 0, format delta, one file of about 6.8 KB.

What to tell the client. Tables are versioned automatically, so we can always ask what the data looked like at an earlier point.

Step 13: Silver inventory with history (SCD2)

Phase 2, Deployment. OSS.

Context. A cell's tilt and software change over time. If you overwrite, you can no longer answer "what was this cell's tilt when the KPI dropped?"

What we did. Removed duplicates, converted text dates to real dates, and checked every cell belongs to a valid site (0 orphans). Built silver.cell in SCD2 form, with effective_from, effective_to and is_current, starting at the site's on-air date.

Why. SCD2 (slow changing dimension, type 2) keeps one row per version of a cell. That is what lets us connect a parameter change to a KPI degradation.

How. build_silver.py with dropDuplicates, to_date, join, SCD2 columns and an orphan check.

What it produced. silver.site 200, silver.equipment 604, silver.cell 604, with 0 orphan cells and one current version per cell.

What to tell the client. We keep a full history of every configuration change per cell, not just today's value. That is what makes root-cause analysis possible.

Step 14: Tilt change recorded as history (and my bug)

Phase 4, Operations (optimization). It updates the Phase 2 cell master. OSS.

Context. On 15 Sep at 02:00 an optimization engineer raises the tilt by 3 degrees on 10 Pune 4G cells. This is planted event 3.

What we did. Closed each old cell version and inserted a new one, so silver.cell went from 604 to 614 rows (604 current). The cells are C00002, 03, 04, 05, 07, 09, 10, 11, 13 and 14, saved in silver.tilt_changes.

Why. A change must be a dated fact in the history so a later KPI drop can be tied to it.

How. apply_tilt_change.py with MERGE INTO (close the old version), INSERT INTO (new version) and RESTORE TABLE ... VERSION AS OF 0. My first script used a temporary view, which re-runs its query. After the update it picked different cells, and 10 cells ended with no current version. The broken_cells check caught it, RESTORE rolled back, and the fix saved the cells in a real table.

What it produced. 614 total rows, 604 current, 0 broken cells. Delta history shows the faulty run, the RESTORE (version 3) and the correct run (versions 4 and 5).

What to tell the client. Even when a step goes wrong, Delta's version history lets us roll back, and the audit trail shows exactly what happened. In operations, that answers "who changed this table, and when?"

Watch out. A view is a saved query that re-runs every time. Use a table when the result must stay fixed.

Step 15: pm_kpi, the expected-answer KPI table

Phase 4, Operations (performance management). OSS.

Context. Performance management (PM) data is the 15-minute health of every cell. A NOC and an optimization team watch it all day.

What we did.

  • Generated 1,739,520 rows: 604 cells x 96 intervals x 30 days (1-30 Sep 2026), with RRC success, drop rate, PRB utilization, throughput and availability.
  • Planted congestion (30 Mumbai cells), the tilt degradation (10 cells) and the fiber cut (15 Pune cells).
  • Saved default.answer_key, which says which cells carry which event.

Why. This became our reference answer. It was a shortcut, because real element managers do not send finished KPIs. Step 16 corrected that.

How. gen_pm_kpi.py with spark.range, crossJoin (cells x time slots), rand and randn, a left_anti join, and saveAsTable("bronze.pm_kpi").

What it produced. Congestion cells at 91.0% evening PRB vs 69.0%. Tilt cells with drop rate 0.5 to 2.5 and RRC success 99.25 to 95.26. Fiber cut: 360 rows with availability 0.

What to tell the client. We built the test set first: known problems at known times, so we can prove the platform finds them rather than just showing charts.

Step 16: PM raw counter files in two vendor formats

Phase 4, Operations (performance management). OSS.

Context. In a real telco, each vendor's element manager (Ericsson ENM, Nokia NetAct) exports raw counters, one file per period, each in its own format.

What we did. Turned pm_kpi into 1,440 files (720 Ericsson, 720 Nokia), one per vendor per hour with four 15-minute intervals each. The vendors use different column names (pmRrcConnEstabAtt vs RRC_CONN_ATT), time formats (2026-09-01T01:15:00 vs 01.09.2026 01:15) and filenames. A 99% success rate became "attempts 3,000, successes 2,978", and the fiber-cut cells have zero counters.

Why. It makes the pipeline realistic: counters in, KPIs calculated later. pm_kpi stays as the answer to reconcile against.

How. gen_pm_files.py with .toPandas() per day, counter maths, 16 parallel uploads and a retry loop. One upload failed on the last day with a transient server error. Adding retries and rerunning the missing days fixed it.

What it produced. 720 Ericsson and 720 Nokia files in raw/pm/.

What to tell the client. Two vendors send two formats. A big part of real OSS data engineering is making them speak one language, and the next steps do that.

Step 17: FM alarm events and Nokia syslogs

Phase 4, Operations (fault management and node logs). OSS.

Context. Alarms do not arrive as a finished table. The fault-management module sends separate RAISE and CLEAR events, and nodes write free-text logs.

What we did.

  • Generated 718 FM files (6,822 events) and 715 Nokia syslog files (5,718 lines such as ... NK-S0012 cell=C00045 ERROR watchdog timeout; cell restart initiated).
  • Planted the fiber cut (15 Critical Link Down alarms, 10:00 to 16:00 on 20 Sep), the Nokia R22.3 problem (1,600 extra alarms from 10 Sep, with matching ERROR log lines), and background noise (1,798 minor and major alarms).
  • 4 alarms are still open at the end of September (RAISE with no CLEAR).

Why. Alarms and logs are two independent evidence sources. When both point at the same cells, the root cause is credible.

How. gen_fm_syslog.py with json.dumps per event, text log lines and retrying uploads. Saved default.alarm_expected as the expected answer.

What it produced. 3,413 alarms (background 1,798, vendor_b 1,600, fiber_cut 15) and 6,822 events (3,413 RAISE, 3,409 CLEAR).

What to tell the client. Faults and logs come from different systems. Our platform correlates them, which is how an engineer would confirm a cause.

Step 18: Auto Loader into bronze (PM, FM, syslog)

Phase 4, Operations (continuous feeds). OSS.

Context. Feeds never stop. The platform must pick up only new files each run and never reload old ones.

What we did. Loaded the files with Auto Loader into four raw bronze tables, kept as text: pm_ericsson_raw (1,048,320 rows, 720 files), pm_nokia_raw (691,200, 720), fm_events_raw (6,822, 718) and syslog_nokia_raw (5,718, 715).

Why. Auto Loader remembers which files it has loaded, in a checkpoint. That makes ingestion incremental and safe to re-run.

How. ingest_feeds.py with readStream.format("cloudFiles"), cloudFiles.schemaLocation, checkpointLocation, trigger(availableNow=True) and toTable.

What it produced. PM rows add up to 1,739,520, exactly pm_kpi. _rescued_data was NULL, so nothing was rejected. A second run gave identical counts and unchanged ingest timestamps, which proves no file was loaded twice.

What to tell the client. New files are picked up automatically and nothing is loaded twice. If the element manager sends a file every 15 minutes, the platform simply keeps up.

Likely question: how is this different from Step 11? Step 11 was a one-time batch read that overwrote the table. Step 18 is incremental, with memory of what it already loaded.

Step 19: Silver PM (harmonize vendors, calculate KPIs)

Phase 4, Operations (performance management). OSS.

Context. Silver is where raw counters from two vendors become one standard KPI table.

What we did. Renamed both vendors' columns to one schema, cast text to numbers and parsed both time formats into real timestamps. Calculated RRC success (succ / att), drop rate (drops / succ), PRB utilization (used / available), throughput (MB x 8 / active secs) and availability (up secs / 900). Reconciled against bronze.pm_kpi.

Why. It proves the whole chain from raw files to KPIs is correct.

How. build_silver_pm.py with to_timestamp using two patterns, cast, unionByName and the KPI formulas.

What it produced. 1,739,520 rows with 0 null timestamps and 0 duplicates. 1,739,160 rows matched the reference (the 360 fiber-cut rows are excluded) with average differences of 0.007 for RRC success and drop rate, 0.0 for throughput and 0.189 for PRB (counter rounding). Rediscovered from raw counters: fiber cut 360 intervals, congestion about 91%, tilt drop rate about 2.5.

What to tell the client. Two vendors, two formats, one standard KPI table. Our calculated KPIs reproduce a reference dataset, which is how we know the pipeline is right.

Step 20: Silver alarm (pair RAISE and CLEAR)

Phase 4, Operations (fault management). OSS.

Context. An alarm's lifecycle is two events. Duration only exists once they are paired.

What we did. Paired RAISE with CLEAR on alarm_id into silver.alarm (3,413 alarms) with raised_ts, cleared_ts, status and duration_min. A left join keeps RAISE events with no CLEAR, which gives 4 OPEN alarms.

Why. The NOC and the SLA report need durations and open alarms.

How. build_silver_fm.py with dropDuplicates, a RAISE/CLEAR split, a left join and a unix_timestamp difference.

What it produced. 3,413 alarms, 4 open, 0 orphan clears, 0 duplicate events. All 3,413 matched alarm_expected with 0 mismatches. Fiber cut: 15 Link Down alarms of exactly 360 minutes. Nokia R22.3 cells went from 0.09 to 0.818 alarms per cell per day (about 9x) while all other cells stayed at 0.099.

What to tell the client. The platform turns a stream of events into alarms with durations. The fiber cut shows up as 15 alarms of exactly six hours, which matches the zero availability in the KPI files. Two independent feeds agree.

Step 21: Silver syslog (parse free text)

Phase 4, Operations (node logs). OSS.

Context. Node logs are unstructured text. To filter and join them, fields must be extracted.

What we did. Parsed each line with a regular expression into ts, site_id, cell_id (null for node-level lines), severity and message, plus a classified event_type. 5,718 rows, 0 unparsed.

Why. Logs corroborate the alarms and let us prove a root cause.

How. build_silver_syslog.py with regexp_extract (5 groups), to_timestamp, when/contains classification, and a join to silver.alarm.

What it produced. Cell Restart 531, Process Crash 548, Recovery 1,078, Alarm Echo 1,251, Routine 2,310. All 1,079 ERROR lines matched an FM alarm on the same cell and second. All of them sit on Nokia R22.3 cells: 0 before 10 Sep, 1,079 after, none on other Nokia cells.

What to tell the client. Alarms and logs independently point at the same Nokia R22.3 software. That is root-cause evidence, not just a correlation in one chart.

Step 22: Trouble tickets (ITSM export) and the fixed as-of date

Phase 4, Operations (ITSM, SLA and MTTR). OSS.

Context. In a NOC, Critical and Major alarms open tickets. MTTR and SLA compliance come from tickets, not from alarms.

What we did.

  • Generated 1,781 tickets (15 P1 from Link Down, 1,766 P2) in 31 daily files. P1 SLA is 4 hours and P2 is 8 hours. Minor alarms open no tickets.
  • Planted the breaches: the 15 fiber-cut tickets take about 6.3 hours, plus 27 random P2 breaches from slow closure.
  • Set an as-of design rule: gold.report_config holds as_of_ts = 30 Sep 23:59:59, and a view ages open alarms to that time.

Why. The data is a fixed September snapshot, so nothing may depend on today's date. No current_date() in silver, gold or dashboards, so the demo works on any day.

How. gen_tickets.py (saved default.ticket_expected) and setup_asof.py (CREATE TABLE gold.report_config, CREATE VIEW gold.open_alarms_at_snapshot).

What it produced. 1,781 tickets, 42 breaches (15 P1 and 27 P2), 3 tickets open. 4 open alarms at the snapshot, aged 0.1 to 2.5 hours (one is Minor and has no ticket).

What to tell the client. This is a September performance review. Views are labelled September 2026, with no live wording, which is how most telco analysis is done anyway: retrospective reviews and post-mortems.

Watch out. My early estimate was about 2,900 tickets. The real count is 1,781, because only Critical and Major alarms open tickets.

Step 23: Silver tickets (MTTR and SLA)

Phase 4, Operations (ITSM, SLA and MTTR). OSS.

Context. Turn the raw ticket export into SLA numbers.

What we did. Loaded the files with Auto Loader into bronze.tickets_raw (1,781 rows, 31 files), then built silver.ticket with resolution_hours, sla_breached, and age_hours_at_snapshot for open tickets, measured to the as-of time.

Why. MTTR and SLA compliance are the headline metrics of a managed-services contract.

How. build_tickets.py with Auto Loader, to_timestamp, a crossJoin with report_config, COUNT_IF and a reconciliation join.

What it produced. 1,781 tickets matched ticket_expected with 0 mismatches. P1: 15 tickets, MTTR 6.3 hours, 15 breaches, 0% compliance. P2: 1,766 tickets, MTTR 1.39 hours, 27 breaches, 98.5% compliance. By team: Transport 15 tickets and 15 breaches, Field 687 and 27, Software/NOC 1,079 and 0.

What to tell the client. The outage shows up as 15 P1 SLA breaches and 0% P1 compliance. The Software/NOC team has the most tickets (1,079, the R22.3 volume) but the fastest resolution, so the bad software costs effort even when it is closed quickly.

Watch out. Ticket T001781 opened at 00:01 on 1 Oct, after the as-of time. It is the edge case behind its age of 0.0.

Step 24: CRM and order-management data

Phase 3, Fulfillment and Activation. BSS.

Context. Phase 3 starts in the BSS: the CRM holds customers, the product catalog holds plans, and the OMS tracks orders to activation.

What we did.

  • Generated 68 files: 6 plans, a base snapshot (38,000 customers), daily new-customer files for the 5G launch (12,000 customers, mostly Pune, 70% on plan P03), 5 weekly change files (2,676 KYC and email updates), a subscription snapshot (50,000 SIMs) and daily order files (12,000 orders).
  • Planted event 5: on 3 Sep 10:00-18:00, 333 of 597 orders never completed (OMS: IN_PROGRESS, subscription: PENDING).
  • Planted event 6: each customer has a hidden home cell that appears in no CRM file. Customers on bad cells churn at 12.0% vs 0.9%.

Why. These are the customer-side facts the OSS data must be linked to. The home cell lives only in default.customer_truth, so the platform has to discover the link on its own.

How. gen_bss.py with Faker (en_IN), pandas and numpy, retrying uploads, and answer tables customer_truth and order_expected. A bug fixed on the way: a NumPy array has no .str accessor, so order IDs use a list comprehension.

What it produced. 50,000 customers, 12,000 orders, 333 stuck. Subscriptions: ACTIVE 47,689, CHURNED 1,978, PENDING 333. 13,991 customers sit on bad cells.

What to tell the client. Customers, plans and orders come from BSS systems. The 5G launch brought 12,000 new customers, and that is when the activation problem hit.

Watch out. Customer names and emails are personal data. They are what we mask in Step 33.

Step 25: Provisioning logs

Phase 3, Fulfillment and Activation. OSS.

Context. After the OMS accepts an order, the OSS orchestrator sends commands to the HSS (subscriber profile), PCRF (policy) and OCS (charging). The logs show why an order is stuck.

What we did. Generated 424 hourly JSON-lines files (36,739 lines). Normal orders (11,439) run HSS, PCRF and OCS within seconds. 228 orders had one HSS ERR_503 and succeeded on retry. The 333 stuck orders show 4 HSS attempts ending in TIMEOUT or ERR_503, with PCRF and OCS never called, and 178 of them end with an orchestrator GIVE_UP.

Why. It is the technical explanation for the OMS and the CRM disagreeing: the activation never completed at the HSS.

How. gen_provisioning.py with order_expected joined to customer_truth for the IMSI, retry and failure rules, and default.provisioning_expected as the answer.

What it produced. Outcomes OK 11,439, OK_AFTER_RETRY 228, STUCK 333. HSS TIMEOUT 779, ERR_503 781, ORCH ABORTED 178.

What to tell the client. When a customer says "my SIM is not working", the order status alone does not say why. The provisioning log shows exactly which network element failed.

Step 26a: Bronze load of BSS and provisioning feeds

Phase 3, Fulfillment and Activation. BSS and OSS.

Context. Same Auto Loader pattern as Step 18, applied to the CRM, OMS and provisioning files.

What we did. Six bronze tables, all text: plans_raw 6, customers_raw 50,000 (31 files), customer_changes_raw 2,676 (5 files), subscriptions_raw 50,000, orders_raw 12,000 (30 files) and provisioning_raw 36,739 (424 files).

Why. Raw and untouched, with audit columns, so typing and cleaning happen in silver.

How. ingest_bss.py with cloudFiles, a checkpoint per table and trigger(availableNow=True).

What it produced. All counts equal what the generators produced, and _rescued_data was NULL.

What to tell the client. Customer and network data now sit in one platform, side by side, with the same lineage and audit columns.

Step 26b: Silver BSS (customer SCD2, subscription, order, provisioning task)

Phase 3, Fulfillment and Activation. BSS and OSS.

Context. Customers change too (KYC status, email). We keep history for them just like for cells.

What we did. Built silver.customer as SCD2: version 1 from registration, plus one version per change, so 50,000 customers have 52,676 rows (50,000 current). Built silver.subscription, silver.order (with activation_minutes) and silver.provisioning_task (one row per order with HSS attempts, failures, whether it reached the OCS, and the outcome).

Why. It links the BSS view of an order to the OSS view of its provisioning.

How. build_silver_bss.py with unionByName, Window plus lead for effective_to, and last(..., True) to carry values forward. My first SCD2 version looped over about 5,000 changes with one SQL statement each and ran for over an hour. The set-based version did the same in minutes. In Spark, think whole-table, not row by row.

What it produced. 12,000 orders matched provisioning_expected with 0 mismatches. Stuck orders 333 of 333. On 3 Sep, 0% of orders are stuck before 10:00 and after 18:00, 47% to 70% are stuck from 10:00 to 17:59, and all 333 fail at the HSS.

What to tell the client. We can name the exact hour the activation problem began and ended, and the network element responsible.

Step 27a: CDR, recharge and complaints (the BSS and OSS bridge)

Phases 3 and 4. BSS and OSS.

Context. A CDR (call detail record) is written per call, SMS or data session and carries the IMSI and the serving cell, so it bridges a customer and a cell. Complaints in a real CRM carry no cell ID, so the link has to go through the CDR.

What we did. Generated 780 files: about 720 hourly CDR files (1,518,380 records for a 10,000-customer sample), 30 recharge files (44,927) and 30 complaint files (6,497). Cells that were down in the fiber cut produce no records. Planted effects: voice drop rate 1.0% on normal cells, 8.5% on tilt-changed cells after 15 Sep, 7.0% on congested cells in the evening, 4.0% on Nokia R22.3 cells after 10 Sep. Bad-cell customers recharge 0.97 times vs 1.19. Complaints per 1,000 customers are 320 vs 51.

Why. It is what ties network problems to customer experience.

How. gen_cdr.py with vectorised numpy and pandas, rng.poisson, hour-of-day weights and per-cause drop probabilities. Saved default.cdr_sample_customers.

What it produced. CDR 1,518,380 rows (Data 759,701, Voice 607,137, SMS 151,542). Complaints 6,497, including 660 "No network" (fiber cut) and 228 "Activation failure" (day-3 bug).

What to tell the client. Every network fault leaves a trace in customer behaviour: dropped calls, complaints, fewer recharges. The CDR is what lets us connect the two worlds.

Watch out. CDRs exist for a sample of 10,000 customers, not all 50,000, to keep the project light.

Step 27b: Bronze and silver for CDR, recharge, complaints, and the churn-link proof

Phases 3 and 4. BSS and OSS.

Context. Load the three feeds, type them, then prove that poor cells drive complaints and churn.

What we did. Loaded cdr_raw (1,518,380 rows, 720 files), recharge_raw (44,927, 30 files) and complaints_raw (6,497, 30 files) with Auto Loader. Built silver.cdr, silver.recharge, silver.complaint and silver.cell_experience (566 cells with voice drop rate, complaints and churn). My first version attributed each customer to every cell they appeared on, which diluted the signal (142 vs 115 complaints per 1,000). Assigning each customer to their most-used cell fixed it.

Why. That is how an operator infers a serving cell. How you attribute a customer to a cell changes the answer a lot.

How. ingest_cdr.py, build_silver_cdr.py and fix_cell_experience.py (a window row_number for the primary cell).

What it produced. The top 30 cells by drop rate are all planted bad cells. Bad cells vs others: drop rate 3.1% vs 0.98%, complaints 331 vs 49 per 1,000 (about 6.8x), churn 12.5% vs 1.0% (about 12x). This is discovered from CDR, complaints and subscriptions, not read from the hidden truth table.

What to tell the client. Customers served by poor cells complain about 7 times more and churn about 12 times more. That connects network investment to revenue protection.

Step 28a: Gold network tables

Phases 1 and 4. OSS.

Context. Silver holds clean records. Gold holds what a NOC lead or optimization engineer actually reads.

What we did. Built gold.cell_health (a 0-100 score per cell, 100 minus penalties for drop rate, RRC success, evening PRB, availability and alarms), gold.worst_cells (top 50), gold.sla_mttr_daily, the view gold.open_tickets_at_snapshot, gold.root_cause_vendor and gold.capacity_plan.

Why. This is the layer the dashboards read, and the capacity plan closes the loop back to Phase 1 (planning).

How. build_gold_network.py with CTAS, CTEs, penalty scoring with LEAST and GREATEST, a window COUNT(*) OVER (PARTITION BY site_id) and a CROSS JOIN with report_config.

What it produced. 604 cells scored: 140 Critical, 464 Healthy. All 140 Critical cells are planted, and no normal cell scored below 100. Worst 50: 26 Evening congestion and 24 Repeated alarms, all planted. SLA in the period: 1,778 tickets and 42 breaches. Capacity plan: 30 Mumbai cells, all in answer_key, 0 false positives (29 "Plan new site / densification", 1 "Add 5G carrier").

What to tell the client. Each cell gets a health score with a stated reason, and the capacity plan turns congestion into a recommendation: where to add capacity or plan a new site. That is how operations feeds back into planning.

Watch out. The fiber-cut cells do not reach the worst 50, because 6 hours down barely dents a monthly availability average. Show the fiber cut from alarms and tickets instead. The planted group counted 153 cells rather than my predicted 149; what matters is that 140 of them score below 95 and no normal cell does.

Step 28b: Gold provisioning and churn risk

Phases 3 and 4. BSS.

Context. The customer-side gold tables behind the last two demo screens.

What we did. Built gold.provisioning_daily (orders, stuck orders, stuck %, activation minutes and HSS failures per day) and gold.churn_risk, a 0-100 score for the 9,997 CDR-sample customers from complaints (20 points each, capped at 40) and the drop rate of their primary cell (capped at 40). Recharges are excluded to avoid data leakage.

Why. A retention team needs to know who to call first.

How. build_gold_customer.py with CTAS, a window ROW_NUMBER for the primary cell, CASE bands and a recall calculation.

What it produced. Only 3 Sep has stuck orders (1,062 orders, 31.4% stuck, 1,338 HSS failures), and normal activation takes about 17 minutes. Churn by band: High 32.5%, Medium 9.4%, Low 1.5%. Flagging High and Medium catches 72.4% of churners while flagging 22.4% of customers.

What to tell the client. A retention team could contact about a fifth of customers and reach almost three quarters of those who would leave.

Watch out. The score is rule-based and was measured on the data it was designed around. Step 32 compares it with a trained model.

Step 29: Lakeflow Declarative Pipeline (PM chain)

Platform.

Context. Instead of running scripts by hand, you declare the tables and quality rules, and Databricks works out the order, runs it and tracks quality. (Formerly Delta Live Tables.)

What we did. Built pipeline nova_pm_pipeline: two streaming tables (bronze_pm_ericsson 1M rows and bronze_pm_nokia 691K rows) using Auto Loader, a materialized view silver_pm_kpi (1.7M rows) that harmonizes both vendors and calculates KPIs with 4 expectations, and gold_cell_daily (18K rows).

Why. Quality rules become part of the pipeline. The four rules are: valid timestamp, successes not above attempts, PRB used not above available, and uptime between 0 and 900 seconds.

How. Pipeline editor with import dlt, @dlt.table, @dlt.expect_or_drop and @dlt.expect, targeting nova_telecom.pipeline. An earlier unsaved draft pipeline had already created the tables, and a table can only be owned by one pipeline ("already managed by pipeline"). The fix was to drop the four tables and run with full table refresh.

What it produced. A green graph with "4 met" on silver_pm_kpi. pipeline.silver_pm_kpi has 1,739,520 rows, equal to silver.pm_kpi from the script.

What to tell the client. This is the production style: declare what you want, set quality rules, and the platform runs and monitors it. A bad record is counted and dropped instead of silently flowing into a report.

Watch out. Open pipelines from Jobs and Pipelines, not from "New", to avoid orphan drafts.

Step 30: Workflow job (nova_daily_refresh)

Platform.

Context. A job runs tasks in order, on demand or on a schedule, and keeps a run history.

What we did. Task 1 run_pipeline (an ETL Pipeline task) triggers nova_pm_pipeline. Task 2 check_counts (a notebook task that depends on Task 1) compares pipeline.silver_pm_kpi with silver.pm_kpi and fails if they differ.

Why. The check turns the job into a data-quality gate. If the pipeline ever drifts from the reference, the job fails visibly.

How. Jobs and Pipelines UI, Run now, then the run graph and task output. The CLI import saved refresh_check.py as a notebook, so we used a Notebook task instead of a Python script task.

What it produced. A manual run that succeeded in about 35 seconds on serverless compute, with output pipeline=1739520 script=1739520.

What to tell the client. The whole refresh is one job with a built-in correctness check, and it can be scheduled so reports update unattended.

Watch out. A daily schedule is not confirmed on Free Edition. Do not claim it is scheduled unless you set it up.

Questions a client will likely ask

  • Is this real data? No. It is a synthetic month built to behave like real OSS and BSS feeds. The dashboard titles say so.
  • How do you know the findings are right? Every planted event has an answer table, and the pipeline outputs were reconciled against them (PM, alarms, tickets, provisioning, capacity plan).
  • Would it work with our vendors and volumes? The pattern holds: vendor-specific bronze, harmonized silver, shared gold. Volumes need sizing on a paid workspace. This project used Free Edition with about 1.7M KPI rows and 1.5M CDRs.
  • Can it run continuously? Auto Loader and the declarative pipeline run incrementally, and a job can schedule them. We built the pattern for the PM chain and ran the job manually.
  • How is customer data protected? Step 33 adds Unity Catalog permissions, lineage and masking of names, emails and phone numbers. It is not built yet.
  • Why bronze, silver and gold? Bronze is the audit copy, silver is the trusted data, and gold is business-ready. Each layer can be rebuilt from the one before it.
