Connecting telecom network operations and customer data on Databricks

A case study: one platform that finds network faults, proves root causes, measures service levels, and links poor network quality to customer complaints and churn.

604cells across 200 sites in four regions
50,000customers, including a 5G launch cohort
4dashboards, from the network operations centre to the boardroom

Overview

A telecom operator runs on two kinds of data that rarely meet. The network side (OSS) records what the network is doing: inventory, performance counters, alarms, logs and trouble tickets. The customer side (BSS) records who the customers are and what they experience: orders, plans, recharges and complaints. Most of the value sits where the two meet, for example in knowing that a customer's complaint comes from a cell that has been dropping calls all week.

This case study follows a fictional mid-size operator, Nova Telecom, over one operating month (September 2026). It operates 200 sites and 604 cells in Pune, Mumbai, Delhi and Bangalore, and it launches a 5G offer in Pune. We built a single Databricks platform for it, from raw files to executive dashboards. This article walks through the challenges, the architecture, how each one was solved, and what a business gets from it.

All data in this case study is synthetic. It was designed to behave like real operator feeds, with realistic problems built into it so that we could verify the platform finds them.

The Challenges

During the month, Nova Telecom faces six operational problems. None of them is exotic. Each is the kind of issue a real operator meets regularly, and each is hard to diagnose when network and customer data live in separate systems.

Network operations

A fiber cut takes cells off air

On 20 September a transport fiber cut takes 15 cells in Pune offline for six hours. Alarms, performance data and tickets all record it, in different systems, and the service-level clock keeps running.

Network operations

A software release degrades one vendor's cells

After a software upgrade on 10 September, 107 cells from Vendor B raise far more alarms than everyone else. The cause is easy to miss in a single chart, and hard to prove without logs.

Optimization

A parameter change backfires

On 15 September an engineer adjusts the antenna tilt on ten cells. Call drops rise on the same day, but nothing in the data connects the two unless configuration history is kept.

Capacity

Evening congestion in Mumbai

Thirty cells exceed 85% radio utilization every evening. This is not a fault. It is a capacity problem, and it needs a planning decision, not a repair ticket.

Customer onboarding

Activations fail during the 5G launch

On 3 September, hundreds of new customers' orders stall between the order system and the network. The order system says "in progress", the CRM says "pending", and customers are left without service.

Customer experience

Poor network quality drives churn

Customers on weak cells complain more and leave more often. But complaints carry no cell identifier, so the connection stays invisible unless the two data worlds are joined.

Underneath these six sit four data problems that any operator will recognise:

  • Two worlds, no join. Network (OSS) and customer (BSS) data sit in different systems, with different keys.
  • Every vendor speaks its own format. Two vendors export the same performance counters with different column names, time formats and file names.
  • The feeds never stop. Files arrive every hour. A platform must load only what is new and never load anything twice.
  • Without history, no root cause. If a configuration change overwrites the old value, nobody can later show what changed before a problem began.

The Architecture

Data moves through four stages on Databricks, governed throughout by Unity Catalog. Each stage can be rebuilt from the one before it, so every number can be traced back to the source file it came from.

  1. Source feeds and landing zone

    Files from every source system arrive in one governed landing area, exactly as the source sent them.

  2. Bronze: raw and traceable

    An untouched copy in Delta tables, stamped with load time and source file. Auto Loader picks up only new files.

  3. Silver: trusted and harmonized

    Cleaned, typed and de-duplicated. Vendor formats become one schema. Configuration and customer history are preserved.

  4. Gold: business-ready

    Cell health, SLA and MTTR, root cause, capacity plan and churn risk, feeding the dashboards.

What flows through it

Network side (OSS)

  • Inventory. Sites, cells, equipment and software versions.
  • Performance counters. Every cell, every 15 minutes, from two vendors.
  • Fault events. Alarm raise and clear events.
  • Node logs. Free-text logs from the equipment.
  • Trouble tickets. From the service-management tool.
  • Provisioning logs. Commands sent to the network when a customer is activated.

Customer side (BSS)

  • CRM. Customers, plans and profile changes.
  • Orders. From the order-management system.
  • Recharges. From billing.
  • Complaints. From customer care.
  • Call detail records (CDR). The bridge. Each record carries a customer and the cell that served them.

A Governed Foundation

Business context. Before any data arrives, a platform needs a clear place for it, with separate zones for raw, cleaned and business-ready data. Without this, teams end up with copies of copies and no way to tell which one is right.

Solution. We created a single Unity Catalog catalog for the operator, with three layers (bronze, silver, gold) and a managed landing area for incoming files. Compute is serverless, and engineers connect from their own editor using Databricks Connect, so code written locally runs on Databricks.

Approach. Catalog, schemas and a volume are created with SQL. Nothing is installed on a server, and the environment is rebuilt from a dependency file.

Outcome. An empty but fully governed structure, ready to receive every feed.

Value add. One place for all operational data, with clear stages from raw to business-ready. If a number looks wrong, it can be traced back to the exact source file.

Network Inventory and Configuration History

Business context. After rollout, the inventory system holds what exists: sites, cells, and the radio equipment on them. Cell settings such as antenna tilt, and the software on the equipment, change over time. If a change overwrites the old value, the history of why a cell behaves differently is lost.

Solution. We loaded 200 sites, 604 cells and 604 equipment records into bronze tables, then built clean silver tables. The cell table keeps a version for every change, with the dates it was effective, so any past configuration can be looked up. When the 15 September tilt change was applied to ten cells, the old version was closed and a new one was opened.

Approach.

  • Raw inventory files are loaded unchanged, with the source file and load time recorded on every row.
  • Silver removes duplicates, converts dates, and checks that every cell belongs to a valid site.
  • Configuration history uses a slowly changing dimension (SCD Type 2) built with Delta Lake MERGE.
  • Delta time travel lets a table be read as it was earlier, or rolled back if a change is wrong.

Outcome. 200 sites, 604 current cells and 604 equipment records, with no orphan cells. After the tilt change, the cell table holds 614 versions (604 current). Software releases are tracked per cell, and Vendor B runs release 22.3 on 107 cells, which no Vendor A cell runs.

Value add. A full history of every configuration change, not just today's value. This is what makes it possible to show that a degradation began right after a specific change.

Performance Management Across Two Vendors

Business context. Each vendor's element manager exports raw performance counters every 15 minutes. The two vendors use different column names, different time formats and different file names, so the same cell counted by two vendors cannot be compared directly.

Solution. We ingested 1,440 counter files (720 per vendor, one per hour) and harmonized them into one standard table. Standard KPIs are then calculated from the counters: RRC success rate, drop rate, radio (PRB) utilization, throughput and availability.

Approach.

  • Each vendor has its own raw bronze table, so nothing is lost or altered on the way in.
  • Silver renames both formats to one schema, casts text to numbers, and parses both time formats into a single timestamp.
  • KPIs are calculated from counters, for example drop rate = abnormal releases divided by successful establishments.
  • The results are reconciled against an independent reference KPI set to prove the chain is correct.

Outcome. 1,739,520 readings (604 cells, every 15 minutes, for 30 days), with no missing timestamps and no duplicates. Calculated KPIs matched the reference within rounding: the average difference was 0.007 percentage points for RRC success and drop rate. From the raw counters alone, the platform rediscovered three of the challenges:

  • The fiber cut appears as 360 cell-intervals with zero availability, on 15 cells for six hours.
  • The congested Mumbai cells run at about 91% evening utilization, against about 69% elsewhere.
  • The ten cells with the tilt change see drop rate rise from about 0.5 to about 2.5 after 15 September.

Value add. Two vendors, two formats, one standard KPI view. Engineers compare cells across vendors with confidence, and the numbers are proven against a reference.

Continuous Ingestion of Operational Feeds

Business context. Operational feeds never stop. A platform that reloads everything each time is slow and risky, and one that misses a file produces silent gaps.

Solution. We used Databricks Auto Loader, which tracks which files it has already processed and loads only new ones. Performance, fault and log feeds all load this way, as do tickets, customer, order, provisioning, CDR, recharge and complaint feeds.

Approach. Each feed has its own checkpoint. A run processes everything that is waiting and then stops, so it can be scheduled or triggered on demand.

Outcome. 1,048,320 and 691,200 performance rows from the two vendors (together exactly the 1,739,520 readings), 6,822 fault events and 5,718 log lines. A second run loaded nothing new, which shows that no file is processed twice.

Value add. New files are picked up automatically and never duplicated. If an element manager sends a file every 15 minutes, the platform simply keeps up.

Fault Management and Node Logs

Business context. Alarms do not arrive as finished records. The fault-management system sends a "raise" event when something fails and a separate "clear" event when it recovers. Equipment also writes free-text logs. Alarms and logs come from different systems, so each one alone is only partial evidence.

Solution. We paired raise and clear events into complete alarms with durations, flagged alarms that were still open, and parsed the free-text logs into structured rows that can be filtered and joined.

Approach.

  • A left join keeps raise events that have no clear yet, so open alarms are never dropped.
  • Regular expressions extract time, site, cell, severity and message from each log line, and classify the event (restart, crash, recovery, routine).
  • Alarms and log errors are correlated on the same cell and second.
  • Both results are checked against reference data.

Outcome. 6,822 events became 3,413 alarms, with 4 still open at month end and no orphan clear events. All 5,718 log lines were parsed. Two findings stood out:

  • Fiber cut. 15 critical Link Down alarms of exactly 360 minutes each, matching the zero availability in the performance data. Two independent feeds agree.
  • Vendor B release 22.3. Alarms per cell per day rose from 0.09 to 0.82 (about nine times) after 10 September, while every other group stayed near 0.1. All 1,079 error log lines sit on those 107 cells, none before the upgrade.

Value add. Root cause with evidence. When alarms and logs independently point at the same release, the conclusion is no longer a hunch, and the vendor conversation can start with data.

Trouble Tickets, SLA and MTTR

Business context. In a managed-services contract, service levels are measured on tickets, not alarms. Critical and major alarms open tickets with a target: four hours for priority 1 and eight hours for priority 2. Penalties follow breaches.

Solution. We loaded 1,781 tickets from daily service-management exports and calculated resolution time, SLA breach and mean time to resolve (MTTR) for each ticket, priority and team. Tickets still open are aged to a fixed reporting date.

Approach. A single configuration table holds the reporting period and the "as of" time (30 September, 23:59:59). Reports and dashboards read their dates from it and never from the system clock, so the review is reproducible on any day.

Outcome.

  • Priority 1: 15 tickets, MTTR 6.3 hours, 15 breaches, 0% compliance. This is the fiber cut.
  • Priority 2: 1,766 tickets, MTTR 1.39 hours, 27 breaches, 98.5% compliance.
  • By team: Transport had 15 tickets and 15 breaches, Field 687 tickets and 27 breaches, and Software/NOC 1,079 tickets and no breaches. The bad software release generates the most tickets, but they close quickly.
  • 3 tickets were still open at the reporting date.

Value add. The cost of an incident is expressed in the terms of the contract: breaches, compliance and mean time to resolve, by team.

Customer Onboarding and Service Activation

Business context. Activating a customer touches both worlds. The order system accepts the order, then the network's provisioning systems have to create the subscriber profile (HSS), the policy (PCRF) and the charging account (OCS). If any step fails, the customer has no service, even though the order looks fine in the CRM.

Solution. We loaded the CRM and order data (50,000 customers, 6 plans, 12,000 launch orders and 2,676 customer profile changes) together with 36,739 provisioning log lines, and built a single view of each order from submission to activation.

Approach.

  • Customer history uses the same slowly changing dimension approach as the cell inventory, so changes such as identity-check status or email are versioned.
  • The customer history is built set-wise using window functions rather than row by row, which turns a job that can take over an hour into a few minutes.
  • The provisioning log is summarised to one row per order: attempts, failures, which system failed, and the outcome.

Outcome. On 3 September, between 10:00 and 17:59, 333 of the day's 1,062 orders (31.4%) never completed. Every one failed at the HSS, with four failed attempts and no call to the policy or charging systems. Before 10:00 and after 18:00 no orders were stuck, and normal activation takes about 17 minutes. The platform confirms that the order system's "in progress" and the CRM's "pending" refer to the same 333 customers.

Value add. The exact window and the exact network element behind an activation failure, instead of a week of back-and-forth between teams.

Linking Customers to the Network

Business context. Customer care records a complaint against a customer, not against a cell. To know whether network quality drives complaints and churn, the customer has to be tied to the cells that serve them.

Solution. The call detail record (CDR) carries both the subscriber and the serving cell, so it bridges the two worlds. We loaded 1,518,380 CDRs for a sample of 10,000 customers, with 44,927 recharges and 6,497 complaints, and assigned each customer to the cell they use most.

Approach. Attributing a customer to every cell they ever touched blurs the signal, because a customer's complaints end up spread across many cells. Using the most-used cell as the primary serving cell, the way operators infer a customer's home cell, restores it.

Outcome. The 30 cells with the highest voice drop rate were all in the affected set. Comparing customers on poor cells with the rest:

  • Voice drop rate: 3.1% against 0.98%.
  • Complaints per 1,000 customers: 331 against 49 (about seven times).
  • Churn: 12.5% against 1.0% (about twelve times).

The complaint categories trace back to the challenges: 660 "No network" complaints from the fiber cut, and 228 "Activation failure" complaints from the stuck orders. These results are discovered by the platform from CDRs, complaints and subscriptions. They are not read from any reference table.

Value add. A clear link between network investment and revenue protection: customers on poor cells complain about seven times more and churn about twelve times more.

Automation: Pipelines and Workflows

Business context. A platform that depends on people running scripts in the right order is fragile. Quality rules that live in someone's head do not protect a report.

Solution. We expressed the performance chain as a Lakeflow Declarative Pipeline: two streaming tables for the vendor feeds, a silver table that harmonizes them and calculates KPIs, and a daily gold summary. Databricks works out the order, runs it and tracks data quality. A Databricks Workflow then runs the pipeline and a verification task that compares its output with the reference.

Approach. Four data quality rules are declared on the silver table: valid timestamp, successes not above attempts, radio blocks used not above available, and uptime within 0 to 900 seconds. A record that breaks a rule is counted and dropped, and not passed silently into a report. The verification task fails the workflow if the two row counts differ.

Outcome. The pipeline ran green end to end and all four quality rules were met. It produced 1,739,520 rows in the silver table, exactly matching the reference, and the workflow completed in about 35 seconds on serverless compute.

Value add. Production-style operation: declared tables, built-in quality rules, a correctness gate, and a run history. The same pattern extends to the other feeds.

The Constraints

  • Synthetic data. The dataset is generated to behave like real operator feeds. Vendor names and software releases are fictional. The results demonstrate the approach and are not a measure of any real operator.
  • A fixed reporting period. The dashboards are a retrospective review of September 2026, with all dates anchored to a configured reporting date. They are not live views.
  • Customer analytics on a sample. CDR-based analysis covers a sample of 10,000 customers. A production deployment would use every customer's CDRs.
  • A rule-based churn score. The churn score is built from business rules and was evaluated on the data it was designed around. A trained and independently tested model is a next step.
  • Declarative pipeline scope. The Lakeflow pipeline covers the performance chain. The remaining feeds were run as scripts using the same patterns, and would move into pipelines for production.
  • Workspace limits. The project ran on Databricks Free Edition, which uses serverless compute and limits some features, including job scheduling. A production workspace needs sizing for real volumes.
  • Hand-written summary text. The findings text on the executive dashboard is written from the verified results and is updated by hand, while the counters beside it are live queries.
  • Governance still to come. Fine-grained access control and masking of personal data (names, emails, phone numbers) are planned and not yet applied.

What Comes Next

  • Machine learning with MLflow. Anomaly detection on cell KPIs, and a churn model trained and tested on separate data, compared with the rule-based score.
  • Governance. Unity Catalog permissions, lineage across the whole chain, and masking of personal data for users without access.
  • Final verification. A last check of every figure against its source, before the platform is presented as complete.
